# IT Audit Report — n8n-nodes-baramundi v0.8.2

**Date**: 2026-04-02
**Auditor Role**: IT Auditor (independent review)
**Scope**: Full codebase, SDLC pipeline, CI/CD, and security posture for
`n8n-nodes-baramundi-management-solution` v0.8.2
**Version Audited**: 0.8.2 (git tag `v0.8.2`, commit `46ca859`)
**npm Status**: Not yet published (pending management approval — REQ-PUBLISH-2)
**Lines of Code**: ~9 000 TypeScript (source), ~1 400 test
**Operations**: ~321 across 6 nodes (BaramundiEndpoint, Asset, Job, Software, Admin, Security)

---

## Executive Summary

The project is **fit for pre-release review** and well-structured for an early-stage
community connector. The codebase follows consistent patterns, has a functioning
SDLC pipeline, and has no critical self-introduced vulnerabilities. The main risks are:

1. **19 npm dependency vulnerabilities**, including 1 CRITICAL (handlebars — transitive,
   no fix currently available; inherited from the n8n peer dependency chain).
2. **Code duplication** of `serverManagement.execute.ts` between two nodes (HIGH maintenance risk).
3. **Inconsistent error handling** — 30 bare `throw new Error()` calls should be
   `NodeOperationError` for correct n8n UX (MEDIUM).
4. **CI/CD hardening gaps** — unpinned GitHub Actions SHAs, no branch protection,
   no automated publish workflow.
5. **Branch coverage at 59.23%** — statement coverage meets the 80% target, but
   branch paths are undertested.

No evidence of hardcoded credentials, injection vulnerabilities in production paths,
or malicious code was found. The security architecture is appropriate for the threat
model.

### CQ-01 — Duplicate serverManagement.execute.ts [HIGH]

**Files:**
- `nodes/BaramundiSecurity/actions/serverManagement/serverManagement.execute.ts`
- `nodes/BaramundiAdmin/actions/serverManagement/serverManagement.execute.ts`

Both files are **byte-for-byte identical**, confirmed by diff. They export the same
set of operations (`getManagementServer`, `getGateway`, `getDipStatus`,
`getVpnAppliance`, `getMicroservices`, etc.) and import from the same shared modules.

**Risk**: Bug fixes or new features applied to one copy will silently diverge from
the other. In a team setting this is a maintainability liability; in a solo project
it is a latent defect risk.

**Recommendation**: Extract to `nodes/shared/actions/serverManagement/serverManagement.execute.ts`
and import in both nodes. One file, one responsibility.

---

### CQ-02 — Bare `throw new Error()` (30 locations) [MEDIUM]

The preferred n8n pattern is `throw new NodeOperationError(this.getNode(), message)`
which attaches the node context, formats the error correctly in the n8n UI, and
respects the `continueOnFail` setting. Bare `Error` throws bypass `continueOnFail`.

**Affected files (sample):**
- `nodes/BaramundiSecurity/actions/serverManagement/serverManagement.execute.ts` (×2)
- `nodes/BaramundiSecurity/actions/defenseControl/defenseControl.execute.ts` (×3)
- `nodes/BaramundiSoftware/actions/variable/variable.execute.ts` (×2)
- `nodes/BaramundiSoftware/actions/software/software.execute.ts` (multiple)

Total: 30 instances vs. 359 correct `NodeOperationError` usages.

**Recommendation**: Replace all 30 instances with
`throw new NodeOperationError(this.getNode(), '<message>')`.

---

### CQ-03 — Silent loadOptions catch blocks [LOW — Accepted]

`nodes/shared/loadOptions.ts`: All 7 `loadOptions` functions catch errors silently
and return empty arrays `[]`. This means a dropdown fails to populate without any
user-visible feedback.

**Rationale for acceptance**: This is the standard n8n loadOptions pattern. Silent
failure allows the workflow editor UI to render the node without a hard error, and
the user can still enter a GUID manually. Surfacing the error here would break the
node editor rather than the execution. Accepted as correct behaviour.

---

### CQ-04 — Branch Coverage 59.23% [MEDIUM]

Statement coverage meets the 80% target. Branch coverage is 59.23% — meaning roughly
40% of conditional branches (if/else, ternary, switch cases) are untested.

**Risk areas** (inferred from coverage report): error paths in `requestApi.ts`,
edge cases in `validation.ts`, and operation-level default branches in execute files.

**Recommendation**: Add tests targeting error paths in `requestApi.ts`
(network failure, 4xx/5xx responses, pagination truncation) and validation edge cases.
Target: branch coverage ≥ 75% before v1.0.0.

---

### CQ-05 — Vitest 1.x → 4.x Upgrade Path [LOW — Deferred]

The project uses Vitest 1.6.x. Vitest 4.x is the current stable release and
includes improved browser mode, snapshot stability, and TypeScript 5.x alignment.

**Assessment**: This is a high-maintenance upgrade. Vitest 2.x and 3.x introduced
breaking changes to the config API and pool configuration. Upgrading mid-phase
would require config migration and potential test rewrites with limited functional
benefit at this stage.

**Recommendation**: Schedule for a dedicated maintenance phase after v1.0.0. Track
as optional task with estimated cost: 1–2 days including test validation.

### SEC-01 — npm Dependency Vulnerabilities [CRITICAL]

**`npm audit` result**: 19 vulnerabilities total (1 critical, 8 high, 10 moderate).

**Critical: `handlebars`** (8 CVEs — GHSA-3mfm, GHSA-2w6w, GHSA-xjpj, GHSA-xhpv,
GHSA-2qvq, GHSA-7rx3, GHSA-442j, GHSA-9cx6)
- JavaScript injection via AST Type Confusion
- Prototype pollution
- DoS via malformed decorator
- **Root cause**: Transitive dependency via `@n8n/node-cli` (build tool only)
- **Production exposure**: handlebars does NOT appear in the compiled runtime bundle
  (`dist/`). It is used only at build time by the n8n node CLI. Risk is limited to
  the developer build environment, not end-user n8n installations.
- **No fix available** in the current `@n8n/node-cli` version tree.

**High: `lodash`** (2 CVEs) — Transitive via `n8n-workflow` peer dependency.
Code injection via `_.template`, prototype pollution via `_.omit`.

**High: `minimatch`** (3 CVEs, ReDoS) — Nested in `@n8n/node-cli`. No fix available.

**Moderate**: esbuild dev-server SSRF (build tool only), langchain SSRF (not used at
runtime in this connector).

**Recommendation**:
1. Monitor `@n8n/node-cli` and `n8n-workflow` for updated releases that patch
   these transitive dependencies.
2. Document the build-time-only scope of critical findings in the README security
   section so that consumers are not misled by `npm audit` output.
3. Add `npm audit --audit-level=critical` to CI with an exception list for known
   build-time-only transitive issues.

---

### SEC-02 — OData Injection [CLOSED — Fixed in v0.8.2]

Previously identified: unsanitised user input in OData `$filter` query strings could
allow injection of additional filter clauses.

**Fix applied** (`validation.ts:316-328`): `validateODataString()` blocks forbidden
characters (`"`, `;`, control chars `\x00–\x1f`). Search functions in `loadOptions.ts`
(lines 165, 203, 241) escape single quotes via `.replace(/'/g, "''")`.

**Status**: Closed. 51 OData filter construction sites reviewed — all validated.

---

### SEC-03 — SSL Bypass (ignoreSslIssues) [LOW — Accepted]

The `Ignore SSL Issues` credential flag sets `rejectUnauthorized: false` scoped to
the individual HTTP request agent, not globally to the Node.js process.

**Positive controls**:
- Default is `false` (secure by default)
- Warning notice shown in n8n UI when enabled: *"TLS validation is disabled — use
  only in isolated test environments"*
- Warning documented in `INSTALLATION.md` and `THREAT-MODEL-2026-04-02.md`

**Accepted risk**: The use case (self-signed certificates on internal bMS servers)
is legitimate and the control is scoped correctly. Accepted.

---

### SEC-04 — SSRF Documentation [INFO]

The `Server URL` field in credentials accepts arbitrary URLs, which is an inherent
SSRF risk when the n8n instance is multi-tenant or accessible to untrusted workflow
authors. This is documented in `THREAT-MODEL-2026-04-02.md` (TB-1 / TA-1).

**Accepted risk**: Standard pattern for all n8n service credentials. Trust boundary
is the n8n workflow author role; RBAC is enforced on the bConnect server side.

### CICD-01 — Unpinned GitHub Actions SHAs [MEDIUM]

`.github/workflows/ci.yml` references Actions by floating tags (e.g.,
`actions/checkout@v4`, `actions/setup-node@v4`) rather than immutable commit SHAs.

**Risk**: A compromised Action tag could execute malicious code in CI with access
to secrets and the npm publish token.

**Recommendation**:
```yaml
# Before
- uses: actions/checkout@v4
# After
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
```
Use Dependabot or Renovate to keep SHA pins updated automatically.

---

### CICD-02 — No Branch Protection on master [MEDIUM]

`master` has no branch protection rules configured on GitHub (no required status
checks, no required reviews, no push restrictions).

**Risk**: Force-pushes, accidental direct commits, or a compromised token could
overwrite master history silently.

**Recommendation**: Enable branch protection:
- Require status checks (CI must pass)
- Restrict force-push
- Require signed commits (or at minimum GPG-signed tags)

Note: As a solo project, "required reviews" is not applicable, but status checks
and force-push protection are still valuable.

---

### CICD-03 — Broad Dependency Version Ranges [MEDIUM]

`package.json` uses `^` ranges (e.g., `"n8n-workflow": "^1.57.0"`) for peer
dependencies. This means `npm ci` in CI may resolve different patch versions over
time.

**Risk**: Silent breaking changes in minor/patch updates could cause CI failures
or subtle runtime regressions between releases.

**Recommendation**:
- Lock exact peer dependency versions in `package.json` for `devDependencies`
- Use `package-lock.json` (already present and committed) — ensure CI uses `npm ci`
  (it does: CI step 2 is `npm ci`) ✓
- Consider Renovate bot for automated, PR-based dependency updates.

---

### CICD-04 — No Automated npm Publish Workflow [LOW — Accepted]

npm publishing is currently manual (`npm publish` from developer machine).
There is no GitHub Actions workflow to publish on tag push.

**Acceptance rationale**: `REQ-PUBLISH-2` is explicitly BLOCKED — baramundi management
approval is required before first publish. Automating publish before approval is
granted would be premature.

**Future recommendation**: After approval, add a release workflow triggered by
`push: tags: ['v*']` that builds, tests, and publishes.

---

### CICD-05 — Git Tags Unsigned in CI [MEDIUM — Mitigated]

Git tags are created manually from the developer machine (not via CI). The v0.8.2
tag was created without GPG signing (`git tag -a v0.8.2`).

**Mitigation in place**: The release tarball itself is GPG-signed
(`v0.8.2.tgz.asc`, RSA-4096, `bernd.wiedemann@baramundi.com`). This provides
artifact integrity verification even without signed tags.

**Recommendation**: Sign git tags: `git tag -s v0.8.2 -m "Release v0.8.2"`.
Long-term: use a corporate code-signing certificate when available from baramundi.

### ARCH-01 — Duplicate serverManagement Module [HIGH]

*(Also reported as CQ-01 — consolidated here for architecture impact.)*

`BaramundiAdmin` and `BaramundiSecurity` both contain identical
`serverManagement.execute.ts` files. The operations (`getManagementServer`,
`getGateway`, `getDipStatus`, `getVpnAppliance`, `getMicroservices`) belong
architecturally to the Admin domain but were duplicated into Security during
module creation.

**Architectural recommendation**: Shared operation modules should live in
`nodes/shared/actions/` and be imported by multiple nodes. This is already the
pattern for `nodes/shared/transport/requestApi.ts` and `nodes/shared/loadOptions.ts`.

---

### ARCH-02 — Router Pattern Consistency [PASS]

All 6 node routers (`BaramundiEndpoint`, `Asset`, `Job`, `Software`, `Admin`,
`Security`) follow an identical dispatch pattern:

1. Extract `resource` and `operation` parameters
2. Iterate input items with try/catch
3. Nested switch: `resource` → `operation` → execute function
4. Default case throws `NodeOperationError` for unknown operations
5. `continueOnFail` wraps item-level errors

`BaramundiEndpoint` and `BaramundiJob` additionally enforce runtime version guards
(lines 19–35 in both routers) to block 25R2-incompatible operations when the user
has selected 26R1, and vice versa. This is the correct implementation.

---

### ARCH-03 — Version Gating Completeness [PASS]

**76 instances** of `bmsVersion` display conditions across all field definition files.
Compliance operations are consistently gated to `['26R1']` only. Operations
available in both versions have no version constraint (correct — no unnecessary
gating).

Runtime guards in routers provide defence-in-depth: even if a field definition
were misconfigured, the router would block execution of version-incompatible
operations with a clear error.

---

### ARCH-04 — API Path Correctness [PASS]

All production API calls use the `/v2.0/` path prefix. No legacy `/v1.0/` paths
were found. The 12 OpenAPI spec files in `/home/ansible/MCP/bConnectOpenAPI/26R1/`
and `/25R2/` serve as the source of truth, and the implementation was verified
against them during Phase 16 (SEC-08 path validation).

**Base URL construction**: `https://<serverUrl>/v2.0/<Resource>` — serverUrl
from credentials, no trailing slash, validated by `validateApiPath()`.

---

### ARCH-05 — Credential Abstraction [PASS]

A single credential type (`BconnectApi`) is shared across all 6 nodes. This means:
- One credential entry per bMS server in n8n
- Consistent auth (Basic Auth), SSL bypass, and timeout configuration
- Single point of change for auth logic

The `testCredentials` method calls `GET /v2.0/endpoints?PageSize=1` — a
lightweight, read-only health check that validates both connectivity and credentials.
